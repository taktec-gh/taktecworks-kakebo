## 方針

- **Step 7 で実運用を開始する。** 機能面は Step 6 で [features.md](./features.md) 冒頭の2つの問い（予算内か / 無駄使いはないか）に答えられる状態になるが、実運用には Vercel へのデプロイ＝公開インターネットへの露出が伴うため、Step 7（認証の強化）を挟んでから始める。以降は使いながら足していく
- 各Stepの完了条件は「機能が動く」ではなく **「機能が動き、そのStep分の単体テストが全て通る」**
- コード実装とテスト作成は**別のエージェント**が担当する

## 順序の根拠

**Step 3（払い出し先）を Step 5（支出登録）より先に作る。**
支出レコードは払い出し先を参照するため、順序を逆にすると支出まわりを作り直すことになる。

**Step 4（予算）を Step 6（ダッシュボード）より先に作る。**
ダッシュボードの表示内容はすべて予算との差分。予算がないと画面の中身が決まらない。

**Step 7（認証の強化）を実運用の開始より先に置く。**
実運用には Vercel へのデプロイが要り、デプロイした時点でアプリは公開インターネットに出る。
Step 1 の認証はパスワード1本で、試行回数の制限がない。ここを塞がずに公開すると、
以後どれだけ機能を足しても土台が緩いままになる。デプロイの前に済ませる。

**Step 8（PWA）は実運用の開始直後に置く。**
ホーム画面から起動できないと、そもそも毎日開かない。分析より優先する。

**Step 9・10 は運用開始後で構わない。**
分析は数ヶ月分のデータが溜まってから意味を持つ。OCRは手入力が回っていれば後回しにできる。

## 各Stepの進め方

実装担当とテスト担当を分けるのは、実装者が自分のコードのテストを書くと実装の都合に合わせた「通るテスト」になりやすく、仕様の抜けを検出できないため。

| エージェント | 役割 | 書き込み可能な範囲 | モデル |
|---|---|---|---|
| `implementer` | そのStepの機能コードを書く（テストは書かない） | `src/`, `prisma/` | 呼び出し元を継承 |
| `tester` | そのStepの単体テストを書き、実行する | `tests/`, `vitest.config.ts` | Sonnet 固定 |

### Step ごとの指示書

各Stepの詳細仕様は `docs/steps/step-N.md` に書き出し、エージェントにはそのファイルを読ませる。プロンプトに仕様を直接埋め込まない。理由は、仕様がリポジトリに残って後から参照でき、implementer と tester が同一の文書を見られるため。

> **Step 1 だけは指示書を先に作らずに実装へ入った。**[step-1.md](./steps/step-1.md) は Step 7 完了後にコミット `df1727f` から復元した**事後の記録**であり、他と性格が異なる。Step 2 以降はすべて実装前に書いている。

### サイクル

```
1. implementer … 機能を実装する
2. コミット     … implementer の成果をここでコミットする（重要・下記）
3. tester      … 仕様（features.md + 実装されたインターフェース）から単体テストを書き、実行する
4. 失敗があれば … tester が失敗内容をレポート → implementer が修正 → tester が再実行
5. 全パス      … 次の Step へ
```

**ルール: tester はテストを緩めて通さない。** 仕様どおりならテストが正しく、実装が誤っている。

### 手順2のコミットを飛ばさない

tester が `src/` を触っていないことを `git status` で検証するには、**その直前のコミットが基準線として必要**。implementer の成果を未コミットのまま tester を走らせると、両者の変更がまとめて「未追跡」として並び、どちらが作ったか区別できなくなる。

（Step 1 で実際にこれを踏み、ファイル更新時刻での事後確認を強いられた。）

### テストに検出力があるかを確認する

tester のテストが初回から全パスした場合、**実装から期待値を逆算していないか**を疑う価値がある。確認方法:

1. 実装コードに意図的にバグを入れる（例: `isPublicPath` が `"/"` に true を返すようにする）
2. `npx vitest run` を実行し、**落ちることを確認**する
3. 実装を元に戻す

落ちなければ、そのテストは何も検出していない。Step 1 ではこの手順で10件が正しく失敗することを確認済み。

> **`npx vitest run` の出力を件数だけに絞り込まないこと。** `FAIL` の行まで残す。
>
> Step 1 と Step 2 で「実装を戻した直後に2件失敗する」現象が出たとき、Vite のトランスフォームキャッシュ（`node_modules/.vite`）のせいだと説明したが、**これは誤りだった**。Step 3 で失敗したテスト名を記録したことで、JWT の署名の末尾1文字を書き換えて改竄を再現するテストに実在する欠陥だと特定できた（base64url の最終文字は上位4ビットしか持たないため `A`〜`D` は同じバイト列になり、改竄が成立しない。1テストあたり 4/64 の確率で失敗する）。
>
> 教訓は2つ。**件数だけを見て原因を推測しない**こと、**再現しない不具合を「フレーキー」と名付けて片付けない**こと。名前を付けた時点で調査が止まる。

### テストの対象範囲

プロジェクト全体。各Stepで追加されたコードすべてに単体テストを付ける。

| 対象 | テスト内容の例 |
|---|---|
| `src/lib/` のロジック | 残高・ペース・着地見込みの計算、日付境界、ゼロ除算、予算未設定時 |
| API Route / Server Action | 正常系、バリデーションエラー、認証なしアクセスの拒否 |
| React コンポーネント | 描画内容、入力操作、予算超過時の表示切り替え |
| Prisma を使う層 | Prisma Client をモックし、クエリ条件と戻り値の変換を検証 |
| 認証 | 正しいパスワードで通る / 誤りで弾く / Cookie改竄で弾く |

`npx vitest run` は毎Step実行し、既存テストのデグレも同時に検出する。

### 単体テストでは絶対に見つからない種類の不具合がある

Step 7 の実機確認で、テストでは検出しようがない問題を2つ踏んだ。**実機確認を省略しない理由**として記録しておく。

**1. アクセスしたURLが違うだけで、パスキーは必ず失敗する。**
PC から Vercel のデプロイ固有URL（`kakebo-<ハッシュ>-....vercel.app`）を開いていたため、ホスト名が `RP_ID` と一致せず、ブラウザがダイアログを出す前に拒否していた。アプリは例外を捕まえて `LOGIN_ERROR_MESSAGE` に落とすので、**画面からは原因が分からない**（それ自体は情報を漏らさないための正しい設計）。パスキーが出てこないときは、まずURLを疑う。詳細は [deploy.md](./deploy.md)。

**2. 署名カウンタを実装しない認証器が実在する。**
スマホ（Android）は認証しても `counter` が 0 のままだった。`isCounterRegression()` で「保存値も新しい値も 0 なら正常」と例外を設けていたが、これが**実機で必要だった**。`newCounter <= storedCounter` の一律判定にしていたら、スマホから二度とログインできなかった。仕様書の記述を実装が守ったから助かったのであって、単体テストは仕様どおりかしか見ていない。**「仕様が現実と合っているか」は実機でしか確かめられない。**

## 人手での確認（実装とは別に実施）

自動テストでは担保できない項目。

1. `npm run dev` → `http://localhost:3000` で起動を確認
2. **スマホ実機での確認**（重要）: 同一LAN内から `http://<PC の IP>:3000` にアクセスし、入力が数タップで完了するかを実機で確かめる。ここが重いと使わなくなる
3. 払い出し先を「現金1件 + クレカ2枚 + 銀行2口座」で登録し、それぞれに予算を設定 → 合計が総予算として正しく出るか確認
4. シードデータ（1ヶ月分のダミー支出）を投入し、ダッシュボードの残高・ペース・着地見込み・払い出し先別残高が手計算と一致するか確認
5. Vercelにデプロイ後、スマホのブラウザからログイン → ホーム画面に追加 → 起動を確認
6. **【2026-08-14 実施済み】** Step 7（パスキーの切り替え）。**この順序でしか実施できない**。WebAuthn の資格情報はオリジンに紐づくため、`localhost` で登録したパスキーは本番ドメインでは使えない。手順と復旧方法は [deploy.md](./deploy.md) に集約した
   1. 本番URLにスマホからパスワードでログイン → パスキーを登録
   2. **PC でもう1本登録**（バックアップ。1本だけだと端末の紛失で締め出される）
   3. 別ブラウザでパスワード単独では入れなくなったことを確認
   4. **締め出しからの復旧手順を実際に試す**: `RECOVERY_MODE=1` を入れてパスワードで入れること、戻したら入れないことを確認する。ここを試さずに運用に入ると、いざというとき使えない
7. Step 10 到達時: 実物のレシート5枚程度をOCRにかけ、日付・店名・金額の抽出精度を目視確認。精度が不十分ならモデル・プロンプトを調整
