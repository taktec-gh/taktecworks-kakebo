## 設計判断（先に決めておくこと）

### `@db.Date` の月範囲検索は UTC 基準で組み立てる

**このStepで最も壊れやすい箇所。**

`Expense.date` は `@db.Date` で、時刻を持たない純粋な日付。Prisma はこれを **UTC 深夜の `Date`** として読み書きする。したがって「2026年8月の支出」を引くときの範囲は次になる。

```
gte: new Date("2026-08-01T00:00:00.000Z")
lt:  new Date("2026-09-01T00:00:00.000Z")
```

**ここで JST の +9 時間を足してはいけない。** 足すと月初・月末の1日がずれる。JST を考えるのは「今日は何日か」「利用者が入力した日付をどう解釈するか」の場面だけで、**保存された値そのものは時刻のない日付**である。

この2つを混同しないよう、日付を扱う純粋関数は**用途ごとに関数を分ける**こと。

- 「今日（JST）の日付」を求める関数 → 現在時刻を引数で受け取る
- 「`"YYYY-MM"` から検索範囲を組み立てる」関数 → UTC 深夜で組み立てる。現在時刻に依存しない

両方に境界テストが要る。

### 入力は「金額 → カテゴリ → 保存」で終わらせる

features.md「入力画面はスマホ前提。金額テンキー → カテゴリ選択 → 払い出し先選択 → 保存」「払い出し先はデフォルト値を持たせ、通常は選び直さなくてよいようにする」。

初期状態を次のようにして、**通常は金額とカテゴリだけ触れば保存できる**ようにする。

| 項目 | 初期値 |
|---|---|
| 日付 | **今日（JST）** |
| 払い出し先 | **既定の払い出し先**（`isDefault: true`） |
| 浪費フラグ | **`NECESSARY`（必要）** |
| カテゴリ | 未選択（必ず選ばせる） |
| 店名・メモ | 空 |

浪費フラグの既定を「必要」にするのは、大半の支出が必要な支出であり、浪費のときだけ1タップ増やすほうが総タップ数が少ないため。**ただし「浪費」を選びやすい位置に置くこと。** 無駄使いの検出がこのアプリの目的の半分なので、押しにくいと記録されなくなる。

### カテゴリは「よく使う順」を先頭に出す

features.md「直近使ったカテゴリ・払い出し先・店名をサジェスト（2回目以降の入力を数タップに）」。

- **直近30日間の使用回数が多い上位5件**をクイック選択として先頭に並べ、その下に全カテゴリを通常の並び順で出す
- 支出が1件も無いうちはクイック選択を出さない（空の枠を見せない）
- 集計の期間と件数は定数として切り出し、変えられるようにする

「直近30日・上位5件」に強い根拠はない。**使ってみて調整する前提の初期値**であることをコードのコメントに残すこと。

店名は入力欄の `datalist` で直近の候補を出す。払い出し先は3件しかないので全件をボタンで並べる。

### 金額は1円以上

予算は「0円の予算」を認めるが、**支出に0円はない**。範囲は **1 〜 99,999,999**。

金額の正規化（全角数字・カンマを受け入れ、小数・マイナスは拒否）は Step 4 の `parseBudgetAmountInput` と同じ規則にする。**ただし下限が違うので流用の仕方に注意すること。** 共通化するか別関数にするかは判断してレポートに書く。

### 日付の範囲は 2000-01-01 〜 今日+1年

打ち間違い（`2206-08-13` など）を弾くための緩い上限。未来日そのものは拒否しない（前払いを記録したい場合がありうる）。

### 削除は確認を挟んだ物理削除

`Expense` は他から参照されないので、無効化の概念は要らない。ただし**スマホでの誤タップを防ぐため2段階**にする（Step 3 の払い出し先の削除と同じ形）。

### 一覧は月単位。絞り込みと並べ替えは URL に持つ

features.md「月切り替え、カテゴリ・払い出し先・浪費タグでの絞り込み、金額順ソート」。

- 月は `/budgets` と同じ **`?month=YYYY-MM`**。不正値・未指定は今月（JST）
- 絞り込みと並べ替えもクエリに持つ（例: `?category=<id>&paymentSource=<id>&waste=WASTE&sort=amount`）。**ブラウザの戻るが効き、URLを共有・ブックマークできる**ため
- 並べ替えは **日付の新しい順（既定）** と **金額の高い順**。features.md「高額順で見ると無駄使いが即座に目に入る」
- **絞り込んだ結果の合計金額と件数を一覧の先頭に出す。** 「今月の外食はいくらか」「浪費だけでいくらか」がその場で分かる
- ページングは入れない。1ヶ月分は多くても数百件で、スクロールで足りる

### 登録できない状態の案内

Step 4 の implementer から引き継いだ懸念。

- **有効な払い出し先が0件**のとき、支出は登録できない。フォームの代わりに `/settings/payment-sources` への案内を出す
- **表示中のカテゴリが0件**のときも同様に `/settings/categories` へ案内する

エラーで落とさず、次にどこへ行けばいいかを示すこと。

### 登録後は入力画面に留まる

レジで続けて2件入力することがある。保存したら**同じ画面に留まり、金額とカテゴリだけクリアして「保存しました」と出す**。日付・払い出し先・浪費フラグは直前の値を保つ（同じ店で続けて買う場面が多いため）。

一覧へ自動で飛ばさない。飛ばすと2件目の入力で毎回戻る操作が要る。

## 実装内容

### 1. 日付の純粋関数 `src/lib/expense-date.ts`

- 今日（JST）の日付を `"YYYY-MM-DD"` で返す（現在時刻は引数）
- `"YYYY-MM-DD"` の検証と、`@db.Date` に渡す `Date`（UTC深夜）への変換
- `"YYYY-MM"` から月範囲（`gte` / `lt`）を組み立てる（UTC深夜）
- `Date` から表示用の文字列（例 `"8/13(木)"`）

`src/lib/year-month.ts` と役割が重なる部分があれば、重複を作らず既存を使うこと。

### 2. 検証 `src/lib/expense-validation.ts`（純粋関数）

金額（1〜99,999,999）、日付（範囲）、カテゴリid、払い出し先id、浪費フラグ、店名（0〜50文字）、メモ（0〜200文字）。

### 3. データ層 `src/lib/expenses.ts`

`PrismaClient` を第1引数で受け取る。

| 操作 | 内容 |
|---|---|
| 一覧 | 月範囲 + 絞り込み + 並べ替え。カテゴリ・払い出し先を `include` |
| 1件取得 | 編集画面用 |
| 作成 / 更新 / 削除 | |
| 直近よく使うカテゴリ | 直近30日の使用回数上位N件 |
| 直近の店名 | 重複を除いた直近N件 |

### 4. 集計 `src/lib/expense-summary.ts`（純粋関数）

絞り込み結果の合計金額・件数・浪費タグ別の内訳。**DBに依存しない**こと（Step 6 のダッシュボードで再利用する）。

### 5. 画面

| パス | 内容 |
|---|---|
| `/expenses/new` | 登録。**アプリで最も使う画面** |
| `/expenses` | 一覧（月切り替え・絞り込み・並べ替え・合計） |
| `/expenses/[id]` | 編集・削除 |

`src/app/page.tsx` から `/expenses/new` と `/expenses` へ辿れるようにする。**登録への導線は最も目立つ位置**に置くこと。

**UI優先事項**
- 金額欄は数字キーボードが出るようにする（`inputMode="numeric"`）
- タップ領域は44px以上、横スクロールしない、ズームせず読める
- 片手で、画面下部だけで入力が完結する配置が望ましい

### Step 3・4 との違い

- Server Action の state は **`{ error: string | null; savedCount: number }`**。`savedCount` は成功のたびに +1 され、フォームはこれが増えたときに金額とカテゴリだけをクリアする（真偽値だと2件目の保存で値が変わらずクリアが走らない）
- `listExpenses` だけは配列ではなく `{ ok, value } | { ok, error }` を返す（月の指定が不正になりうるため）

### 特に確認したい観点

壊れると被害が大きい順。

1. **`getMonthDateRange` の UTC 境界** — `"2026-08"` → `gte` = `2026-08-01T00:00:00.000Z`、`lt` = `2026-09-01T00:00:00.000Z` ちょうど。`"2026-12"` の `lt` が翌年になること。**実行環境の TZ に依存しないこと**
2. **`getCurrentDate` の JST 境界** — `2026-08-13T14:59:59Z` → `"2026-08-13"`、`15:00:00Z` → `"2026-08-14"`。年またぎも
3. **`toDbDate` / `fromDbDate` の往復で1日ずれないこと**
4. **`listExpenses` が `where.date` に UTC 深夜の範囲を渡すこと**、および**絞り込みが指定されていない軸を `where` に入れないこと**（`categoryId: undefined` を入れると意図しない結果になる罠）
5. **金額の境界** — 0 は拒否、1 は可、99,999,999 は可、100,000,000 は拒否。空欄は**エラー**（予算と違い「未設定」にならない）
6. **`parseBudgetAmountInput` が Step 4 と完全に同じ挙動のままであること** — 共通化が壊れていないことの検出。特に空欄 → `{ ok: true, value: null }`、`"0"` → `0`
7. **日付の範囲と実在判定** — `2000-01-01` の境界、今日+1年の境界、`2026-02-30` を弾くこと、うるう年（`2024-02-29` 可 / `2026-02-29` 不可）
8. **`selectQuickPickCategoryIds`** — 回数降順、同数なら表示順が先を優先、一覧に無い id を落とす、上限の切り捨て
9. **`summarizeExpenses`** — 空配列で `byWasteTag` の3キーがすべて 0件0円で存在すること
10. **`parseExpenseListFilter`** — 配列パラメータ・空文字・不正値がすべて既定へ落ちること。`parse → build → parse` が同じ結果になること
11. **Server Action** — 全アクションの認証。`savedCount` が成功時のみ +1。`deleteExpenseAction` が失敗時に redirect しないこと
12. **`ExpenseForm`** — `savedCount` が増えたとき `create` では金額とカテゴリのみクリアされ、日付・払い出し先・浪費フラグ・店名・メモが保たれること。`edit` では何もクリアされないこと
13. **登録できない状態の案内** — 有効な払い出し先0件、表示中カテゴリ0件のとき、フォームではなく設定画面への案内が出ること

### テストの方針

Step 2〜4 と同じ。**単体テストから実データベースに接続しない。**
