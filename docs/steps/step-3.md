## 設計判断（先に決めておくこと）

実装前に読むこと。ここが曖昧なままだと作り直しになる。

### 削除は「参照がゼロのときだけ」許す

features.md が挙げているのは **追加・リネーム・並べ替え・無効化**であって削除ではない。過去の支出が参照している払い出し先を消すと家計の履歴が壊れるため、原則は無効化。

ただし打ち間違いで作ってしまった行を永久に抱えるのも困るので、**`Expense` も `Budget` も1件も紐づいていない払い出し先に限り削除を許す。**

- 参照がある場合は削除を拒否し、「無効化してください」と案内する
- `Budget` は `onDelete: Cascade` なので、予算が設定されたまま削除すると予算が黙って消える。**予算が1件でもあれば削除は拒否する**

### 既定の払い出し先は常にちょうど1件

features.md「払い出し先はデフォルト値を持たせ、通常は選び直さなくてよいようにする」。DB 側は部分ユニークインデックスで「`isDefault = true` は最大1件」を保証しているが、**「最低1件」はアプリ層の責任**。

- 既定を切り替えるときは**必ずトランザクション内で、旧既定を `false` にしてから新既定を `true` にする**。順序が逆だと部分ユニークインデックスに衝突して P2002 になる
- **既定の払い出し先は無効化も削除もできない。** 先に別のものを既定にしてもらう
- **無効な払い出し先を既定にはできない**

### 有効な払い出し先を全部は無効化できない

支出登録には有効な払い出し先が最低1件必要（Step 5）。有効なものが1件しかないとき、それを無効化することはできない。

### 並べ替えは「上へ / 下へ」ボタン

スマホでのドラッグ&ドロップは誤操作しやすく、実装コストも高い。1画面に並ぶ件数はカード数枚 + 口座数個で、多くても10件程度なのでボタンで足りる。

- 一覧は **「有効」グループ → 「無効」グループ**の順に表示し、各グループ内は `sortOrder` 昇順
- 移動は**同一グループ内でのみ**。グループの端では該当ボタンを非活性にする
- `sortOrder` は隙間を作らず連番を保つ

### 並べ替えの計算は純粋関数に切り出す

DB に触れる処理と混ぜない。`(一覧, 動かす id, 方向) → 新しい sortOrder の割り当て` を返す純粋関数にすること。テストがモックなしで書けるようにするため。

## 実装内容

### 1. データ層 `src/lib/payment-sources.ts`

`PrismaClient` を**引数で受け取る**形にする（`src/lib/seed.ts` と同じ方針。テストからモックを差し込めるようにするため）。

必要な操作:

| 操作 | 内容 |
|---|---|
| 一覧取得 | 有効→無効の順、各グループ内は `sortOrder` 昇順 |
| 作成 | `sortOrder` は既存の最大 + 1。`isDefault` は常に `false`（既定化は別操作） |
| リネーム | `name` のみ変更 |
| 既定の変更 | トランザクションで旧既定を落としてから新既定を立てる |
| 有効/無効の切り替え | 上記の禁止条件を満たすときのみ |
| 並べ替え | 純粋関数の計算結果をトランザクションで反映 |
| 削除 | 参照ゼロのときのみ |

### 2. 入力値の検証 `src/lib/payment-source-validation.ts`（純粋関数）

- `name`: 前後の空白を `trim` してから検証。**1〜30文字**。空は不可
- `name` の重複は DB の `@unique` に任せ、**P2002 を捕まえて利用者向けメッセージに変換**する。大文字小文字や全角半角の正規化はしない（利用者は本人1人だけなので過剰）
- `type`: `CASH` / `CREDIT_CARD` / `BANK_DEBIT` のいずれか。フォームから来た文字列を enum に照合し、外れていれば拒否する

検証結果は「成功なら正規化済みの値、失敗なら日本語のメッセージ」を返す形にする。例外で制御しない。

### 3. Server Actions

Step 1 の `src/app/(auth)/login/actions.ts` と同じ `{ error?: string }` を返す形に揃える。成功時は `revalidatePath` で一覧を更新する。

- 作成 / リネーム / 既定の変更 / 有効・無効の切り替え / 並べ替え / 削除

**禁止条件に触れた操作は例外を投げず、利用者に理由が伝わる日本語メッセージを返す。** 例:
- 「既定の払い出し先は無効にできません。先に別の払い出し先を既定にしてください。」
- 「この払い出し先には支出が記録されているため削除できません。無効化してください。」

### 4. 画面

| パス | 内容 |
|---|---|
| `/settings/payment-sources` | 一覧 + 新規追加フォーム |
| `/settings/payment-sources/[id]` | 編集（リネーム / タイプ変更 / 既定にする / 無効化 / 削除） |

編集を別ページにするのは、一覧内にインライン編集を詰めるとスマホでタップ対象が小さくなるため。

**一覧に出す情報**: 名前 / タイプ（現金・クレカ・銀行引き落としが一目で分かる表示）/ 既定バッジ / 無効バッジ / 上へ・下へボタン。

`src/app/page.tsx` からこの設定画面へ辿れるようにする（暫定のリンクでよい。Step 6 でダッシュボードに置き換わる）。

**UI優先事項**（`.claude/agents/implementer.md` の規約に従う）
- 片手で押せるタップ領域
- 横スクロールしない
- ズームせずに読める文字サイズ

### 5. Prisma のエラーコード

step-2.md の実測どおり、ドライバアダプタ経由では従来と異なるコードが返る。

- 名前の重複 → **P2002**
- 参照がある行の削除 → **P2039**（P2003 ではない）

削除は事前に参照件数を数えて拒否する設計なので P2039 には通常到達しないが、競合したときのフォールバックとして捕まえておくこと。

## 実装完了後の引き継ぎ（tester 向け）

implementer の実装が完了した時点の事実を記録する。**期待値の根拠は上の仕様であって、この節ではない。** この節は「何がどう呼べるか」を知るためのもの。関数のシグネチャは実ファイルを読んで確認すること。

### モジュール構成

| ファイル | 役割 | テストのしやすさ |
|---|---|---|
| `src/lib/payment-source-validation.ts` | 名前・タイプ・id の検証 | 純粋関数。モック不要 |
| `src/lib/payment-source-order.ts` | 並べ替えの計算 | 純粋関数。DB非依存 |
| `src/lib/payment-sources.ts` | データ層 | 第1引数の `PrismaClient` をモックする |
| `src/app/settings/payment-sources/actions.ts` | Server Action | 下記のモックが必要 |
| `src/app/settings/payment-sources/*.tsx` | 画面 | props でアクションを受け取るのでモック可能 |

### 実装上の約束ごと

- 結果は例外ではなく **`{ ok: true, value } | { ok: false, error }`** で返る。エラー文言は `PAYMENT_SOURCE_ERRORS` / `PAYMENT_SOURCE_VALIDATION_ERRORS` / `PAYMENT_SOURCE_ORDER_ERRORS` に定数として置かれている
- Server Action の戻り値は `{ error: string | null }`（Step 1 のログインと同形）。例外は投げない
- Prisma のエラーは `instanceof` ではなく **`error.code` の文字列**で判定している。テストでは `Object.assign(new Error("x"), { code: "P2002" })` で再現できる
- 名前の文字数は `Array.from(name).length`（**コードポイント単位**）で数える
- 並べ替え・削除の結果は常に**一覧の全件**に `sortOrder = 1..n` を振り直したものになる
- リネームとタイプ変更は `updatePaymentSource` に統合されている（`renamePaymentSource` は存在しない）

### Server Action のテストに必要なモック

`@/lib/session`（`getSession`）、`@/lib/prisma`、`next/cache`（`revalidatePath`）、`next/navigation`（`redirect`）。

**全 Server Action が先頭で `getSession()` を呼び、null なら `/login` へ redirect する。** Server Action は POST エンドポイントとして直接叩けるため、画面側の保護だけでは不十分だという判断による。この挙動自体もテスト対象。

### 特に確認したい観点

仕様上こわれると被害が大きい順。

1. **`setDefaultPaymentSource` が `$transaction` に渡す配列の順序** — 旧既定を `false` にする `updateMany` が先、新既定を `true` にする `update` が後。逆順だと部分ユニークインデックスに衝突して P2002 になる
2. **`calculateReorder` のグループ境界** — 有効グループの末尾で「下へ」、無効グループの先頭で「上へ」がいずれも拒否されること。無効グループへ飛び越さないこと
3. **`canMovePaymentSource` と `calculateReorder` の可否判断が常に一致すること** — 片方だけ直すと画面のボタン状態と実処理がずれる
4. **無効化の境界** — 有効が1件のときは拒否、2件なら可。既定は常に拒否。有効化のときは件数を検査しないこと
5. **削除の判定順序** — 既定 → 支出あり → 予算あり。それぞれ別の文言
6. **`deletePaymentSourceAction` が失敗時に redirect しないこと**
7. 入力が未ソート・`sortOrder` に欠番や重複がある一覧を渡しても、結果が 1..n の連番になること。引数を破壊しないこと
8. 空テーブル（`_max.sortOrder` が null）で作成すると `sortOrder = 1` になること

### テストの方針

Step 2 と同じ。**単体テストから実データベースに接続しない。** `.env` がなくても走る状態を保ち、Neon の共有データを書き換えず、無料枠の CU-hours も消費しないため。
