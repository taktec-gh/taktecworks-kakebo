# 公開用家計簿アプリ 設計方針

個人用の家計簿アプリ（kakebo）を、複数人が安全に使えるポートフォリオ用デモとして作り直すための設計方針。
**ここに書くのは「決めたこと」と「その理由」。** 決めた日付を残し、前提が変わったら見直す。

- 決定日：2026-09-14
- 元になった単一ユーザー版は非公開。**そちらのコード・DB・履歴には触れない**

---

## 決定事項

### 1. 位置づけ：ポートフォリオ用のデモ

実際のサービスとしては提供しない。発注を検討している人に「業務Webアプリを安全に作れる」ことを示すための実物。

帰結：

- 利用規約とプライバシーポリシーは最小限にする（デモであること／データは予告なく削除されうること／**実在の家計情報を入力しないでほしいこと**）
- 可用性やデータ復旧への要求は低い
- **ただしセキュリティは手を抜かない。** 見られるのはそこだから

### 2. 閲覧者の体験：訪問者ごとの使い捨てデモアカウント

「デモで試す」ボタンを押すと、サンプルデータ入りのアカウントがその場で作られ、一定時間後に自動で削除される。

**共有のデモアカウントにしない理由。** 全員が同じアカウントを触ると、誰かが店名やメモに不適切な文字を書いたとき、次に見に来た発注者にそれが表示される。荒らされたデモを見られるのはポートフォリオとして最悪の事態。使い捨てなら他の訪問者の書き込みは見えず、**訪問者自身の体験がそのままデータ分離の実演になる。**

> **絶対条件：デモ用の入口は、デモ用に作ったユーザー以外のセッションを発行できないように作る。**
> ユーザーIDを外部（フォーム・URL・Cookie）から受け取る作りにすると、任意のユーザーになりすませる裏口になる。

必要なもの：

- サンプルデータの生成（サインアップ時の初期データ投入と同じ処理を流用）
- 期限切れデモユーザーの自動削除（Vercel Cron）
- デモアカウント作成のレート制限（DBの食い潰し対策）
- ~~未決：有効期限の長さ（例：24時間）、デモユーザーにパスキー登録を許すか~~ → 決定事項 8（24時間、登録は許さない）

### 3. 認証：パスキーのみ ＋ リカバリーコード。メールアドレスは持たない

- **パスワードは一切持たない。** 個人用の `APP_PASSWORD`（全体で1本）と `RECOVERY_MODE`（環境変数で全体のパスワードログインを開ける）は廃止する。どちらも「利用者は1人」前提の仕組み
- **ログインではユーザー名を入力させない。** パスキー側でアカウントを選ばせる。ユーザー名を持たなければ、「このユーザー名は存在する」と攻撃者に教える経路（ユーザー列挙）自体が生まれない
- **メールアドレスを持たない。** デモなので預かる理由がなく、持たなければ漏れようがない。送信基盤や確認メールの仕組みも不要になる
- **個人用のパスキー実装はそのまま流用する。** チャレンジの単回性、署名カウンタを実装しない認証器への例外（実機で必要だった）まで含めてテスト済み

**リカバリーコード**（パスキーを全部失ったときの逃げ道。GitHubやGoogleと同じ方式）：

- サインアップ時に**一度だけ**表示する
- DBには**ハッシュだけ**を保存する
- **1回使ったら無効**にし、使用後は新しいパスキーの登録を必須にする
- ユーザー名なしでコードからアカウントを特定するため、コードは十分な長さのランダム値にし、~~**鍵付きハッシュ（HMAC）**~~ ハッシュで索引検索する（→ 決定事項 10 で**鍵なしの SHA-256** に変更）
- **スケジュールが押したら、MVPから最初に削る。** その場合は「複数のパスキーの登録を促す」だけで出す

入れる理由：発注を検討する人は「パスキーをなくしたらどうなるの？」と必ず聞く。そこに設計で答えられることがポートフォリオの価値になる。

### 4. データ分離：`userId` を明示的に渡す ＋ 分離テストで網羅を保証

複数ユーザー化の本丸。**難所は認証ではなくデータ分離。** 個人用は `deleteExpense(prisma, id)` のようにIDだけで行を操作しており、そのまま複数ユーザーにすると、他人の支出IDを推測するだけで閲覧・編集・削除できる（IDOR）。

- **全データ操作関数のシグネチャを `(client, userId, ...)` にする。** 個人用がDBクライアントを引数で受け取る作りで統一されているので、その自然な延長になる
- **`userId` はセッションからしか作れない専用の型（ブランド型）にする。** フォームから来た文字列をうっかり渡すとコンパイルが通らない。付け忘れを型で防ぐ
- **更新・削除は `where: { id, userId }` で条件に含める。** 取得してから持ち主を比べる方式にしない（その間に状態が変わる隙ができる）
- **関連先の持ち主も検証する。** 支出登録時の `categoryId` / `paymentSourceId` が自分のものか確認しないと、他人のカテゴリに自分の支出をぶら下げられる
- **他人のIDには「存在しない」と同じ応答を返す。** 「権限がない」と返すと、そのIDが実在することが漏れる

分離テスト：

- 利用者A・Bを用意し、**全Server Actionについて**、Aのセッションで Bの支出・収入・予算・カテゴリ・払い出し先・パスキーを閲覧／編集／削除できないことを表形式で漏れなく検証する
- **検出力を確認する。** `userId` の絞り込みをわざと外し、テストが落ちることを確かめる（個人用 `docs/roadmap.md` と同じ手順）

**PostgreSQL の RLS（行レベルセキュリティ）は今回は入れない。** DB側で強制できるので防御としては最強だが、Neonのプール接続ではリクエストごとにトランザクションを張って利用者IDを設定する必要があり、Prismaとの組み合わせが複雑になる。さらに**RLSはモックでは検証できず実DBでの結合テストが要る**（既存テストはモックベース）。2〜3週間の枠では費用に見合わない。受注後の強化候補として残す。

### 5. ドメイン：Vercel の無料ドメイン

- プロジェクト名（候補）：**`taktecworks-kakebo`** → `taktecworks-kakebo.vercel.app`
- **最初のデプロイ前に確定し、以後変更しない。** URLがパスキーの `RP_ID` になり、変えると登録済みのパスキーが全部無効になる（個人用 `docs/deploy.md` の教訓）
- 屋号を含めると他人のプロジェクト名と被りにくい（単一ユーザー版では希望した名前が他人に取られていて、別名が付いた）
- **公開前に Vercel Hobby（無料）プランの規約を確認する。** 非商用利用が条件で、個人事業の営業に使うポートフォリオが該当するかは読み方次第
- **2026-09-19 確定：プロジェクト名は `taktecworks-kakebo`、Hobby プランで使う（利用者の判断）。**
  - 規約（Fair Use Guidelines、2026-09-14 更新）は商用利用を「目的」で定義しており（"used for the purpose of financial gain"）、例に "Advertising the sale of a product or service" がある。グレーと判断した
  - アプリには受注の告知・価格・広告・事業サイトへのリンクを置かない。問題にされたら Pro に切り替える
- **Cloudflare（Workers）は採らない（2026-09-19）。** Next.js 16 の `proxy.ts` は Node.js ランタイム固定で、OpenNext の Cloudflare 版は Node の Middleware に未対応（公式文書）。認証と CSP の nonce を担う proxy を作り直すことになる

### 6. データ分離の実装で決めたこと

- 決定日：2026-09-19（公開版 Step 1。詳細と根拠は [steps/pub-1.md](./steps/pub-1.md) の設計判断）

| 決めたこと | 理由 |
|---|---|
| **`User` は最小限**（id と日時だけ）。表示名・メールアドレス・デモかどうかは必要になる Step で足す | 持たないものは漏れない（決定事項 3） |
| **`User` を消すと全データが消える**（`onDelete: Cascade`） | デモユーザーの自動削除（決定事項 2）がこの前提に乗る。支出のあるユーザーを削除できることは実DBで確認済み |
| **`LoginAttempt` だけは `userId` を持たない** | ログイン前（誰か分からない時点）の IP 単位の記録だから |
| **関連の持ち主をDBの複合外部キーで強制する**（`Expense(categoryId, userId) → Category(id, userId)` など） | 他人のカテゴリに自分の支出をぶら下げることを、アプリの確認だけに頼らずDBで不可能にする。アプリ側の確認はエラー文言のために残す |
| **名前のユニーク・既定の払い出し先・採番をユーザー単位にする** | 全体のままだと2人目のユーザーがプリセットを持てない／既定の切り替えで他人の既定が外れる |
| **`UserId` を作れる場所は3箇所**（セッション検証・パスキー認証の成功後・ユーザー作成）。テストが `src/` を走査して検査する | `as UserId` はどこでも書けるので、型だけでは付け忘れを防ぎきれない |
| **セッション JWT は `typ` ヘッダでチャレンジ JWT と区別する** | `sub` がユーザーIDになり、`sub` の値だけでは用途を区別できなくなった |
| **パスワードログインと `RECOVERY_MODE` はデータ分離と同時に廃止した** | 全体で1本のパスワードでは「誰としてログインさせるか」を決められない。固定のユーザーIDを持たせると裏口になる |
| **開発用のログイン口（ユーザーIDを指定してセッションを発行する経路）は作らない** | 「開発時だけ有効」の分岐は、設定の取り違え1つで本番に残る裏口になる |
| **セッションのユーザーがDBに存在するかは、まだ照合しない** | 毎リクエストのクエリが増える。個別失効（世代番号）と一緒に扱う。消えたユーザーのセッションでもデータは漏れない（一覧は空、作成は外部キー違反） |
| **分離は単体テスト（偽 Prisma クライアント）＋実DBの検証スクリプトで保証する** | 単体テストはモックなので、複合外部キー・部分ユニーク・カスケードが PostgreSQL で効くことは保証できない |

### 7. サインアップで決めたこと

- 決定日：2026-09-19（公開版 Step 2。詳細と根拠は [steps/pub-2.md](./steps/pub-2.md) の設計判断）

| 決めたこと | 理由 |
|---|---|
| **リカバリーコードは独立した Step にし、削れる形にする** | 公開日までにデモアカウント・セキュリティヘッダー・デプロイが残る。無い間は「別の端末も登録してほしい」と登録の前に伝える |
| **ユーザーはパスキーの検証が済んでから作る**。ユーザー・プリセット・資格情報・登録記録を1つのトランザクションで作る | 途中離脱やボットで、誰もログインできないユーザーを残さない |
| **WebAuthn のユーザーID（user handle）はユーザーごとの32バイトの乱数**（`User.webauthnUserId`）。内部の `User.id` を認証器に渡さない | 同じ利用者の2本目のパスキーが別アカウントに見えないように。同期されるパスキーで内部IDを外に出さない |
| サインアップ中の user handle は**署名付きの短命 Cookie**に置き、用途（サインアップ / 設定画面の登録 / ログイン）ごとに `sub` と Cookie 名を分ける | 応答やフォームから受け取ると、他人の user handle で資格情報を作れる |
| パスキーの表示名は user handle から決まる `家計簿 #XXXX` | 同じ端末に複数アカウントがあっても選択画面で見分けられる。名前やメールアドレスは持たない |
| **ログイン時に user handle と資格情報の持ち主を照合する** | 他人の資格情報に自分の user handle を付けた応答を通さない |
| **サインアップは IP 単位（1時間3件）と全体（24時間100件）で制限する**。数えるのは作られたアカウント | ソフトウェアの認証器で登録は自動化できる。全体の上限は正規の利用者も止めうるが、デモなので DB を守るほうを取る |
| **`SignupEvent` は `userId` を持たない**（`LoginAttempt` に続く2つ目の例外） | アカウントを消すたびに記録が消えると、「作って消す」で制限を回避できる |
| **アカウントはパスキーで決まる。** 別の端末では QR コードでログインしてからパスキーを追加する。その案内をログイン・サインアップ・設定画面に出す | 新しい端末でサインアップすると別アカウントになる。サーバーは同じ人かを見分けられない |

### 8. デモアカウントで決めたこと

- 決定日：2026-09-19（公開版 Step 3。詳細と根拠は [steps/pub-3.md](./steps/pub-3.md) の設計判断）。決定事項 2 の未決事項への答えを含む

| 決めたこと | 理由 |
|---|---|
| **デモユーザーは `User.demoExpiresAt` で表す**（`null` なら通常ユーザー）。作成後に変えない | 期限の無いデモも期限のある通常ユーザーも作れない形にする。延長や切り替えの経路が、期限の無効化や通常ユーザーの削除につながる |
| **期限は24時間。デモのセッションの有効期限を同じ時刻にする** | 削除は1日1回なので最大1日ほど残るが、その間もセッションが切れていて期限切れのデータに触れない |
| **デモの入口は引数を読まず、今作ったユーザーにだけセッションを発行する** | 決定事項 2 の絶対条件。変異テストで FormData のユーザーIDを使わないことを確認済み |
| **デモ作成は IP 単位（1時間5件）と全体（24時間300件）で制限する。** `DemoEvent` は `SignupEvent` と分け、`userId` を持たない | デモの連打でサインアップの枠を埋めない。記録をユーザーと一緒に消さない |
| **期限切れのデモユーザーは1日1回の Vercel Cron で削除する。** 条件は `demoExpiresAt` が `null` でなく、かつ現在より前 | 通常ユーザーを消す経路を条件の読み違いで作らない。実DBの検証スクリプトでも確認 |
| **Cron は `CRON_SECRET` の Bearer で認証し、未設定・空なら何もしない** | 未設定のときに誰でも削除を叩ける状態にしない |
| **記録の保持期間: `SignupEvent` / `DemoEvent` は7日、`LoginAttempt` は30日**。同じ Cron で消す | レート制限の時間窓より十分長く。ログイン試行は攻撃に気づくために長めに残す |
| **ログアウトではデモユーザーを消さない** | ログアウトに「ユーザーを消す」経路を足すと、取り違え1つで通常ユーザーの全データ削除になる |
| **デモユーザーはパスキーを登録できない**（Server Action で DB を見て拒否） | デモが消えても OS のパスキーは残る。デモを通常アカウントとして使い続ける経路にもなる |
| **サンプルデータは今日の日付から決まる純粋関数で作り、乱数を使わない** | どの日に作っても「予算内か / 無駄使いはないか」に答えが出ることを、全日付でテストできる |

### 9. セキュリティヘッダーで決めたこと

- 決定日：2026-09-19（公開版 Step 4。詳細と根拠は [steps/pub-4.md](./steps/pub-4.md) の設計判断）

| 決めたこと | 理由 |
|---|---|
| **CSP は nonce 方式で、proxy がリクエストごとに生成する。** 本番に `'unsafe-inline'` / `'unsafe-eval'` を入れない | インラインを全部許すと XSS で差し込まれたスクリプトも動く。家計データを扱うので厳格にする |
| 開発だけ緩める判定は `NODE_ENV === "development"` の一致 | 「production でなければ緩める」だと、未設定や test で緩いポリシーになる |
| **`upgrade-insecure-requests` は入れない** | ローカルの http での `next start` が壊れうる。本番は Vercel の https 強制と HSTS で足りる |
| **全ページを動的レンダリングにする**（ルートレイアウトの `connection()`） | 静的なページには nonce が入らず、本番でスクリプトが全部ブロックされる |
| **`src/` にインラインの `style` を置かない**（予算バーは SVG、404 画面は自前） | `style-src` に例外を作らない。テストが `src/` を走査して検査する |
| その他のヘッダーは `next.config.ts`（HSTS・X-Frame-Options・nosniff・Permissions-Policy・COOP）。`X-Powered-By` は消す | 静的ファイルを含む全パスに付ける |
| **`Referrer-Policy` は `strict-origin-when-cross-origin`**（`no-referrer` にしない） | `no-referrer` は同一オリジンの POST の Origin を `null` にしうり、Server Actions の Origin チェックを壊す |
| CSP は強制モードで出し、違反の報告の受け口は持たない | 受け口が無ければ Report-Only で様子を見ても結果を集められない。本番ビルドの実機確認で違反0件を確かめた |

### 10. リカバリーコードで決めたこと

- 決定日：2026-09-19（公開版 Step 5。詳細と根拠は [steps/pub-5.md](./steps/pub-5.md) の設計判断）

| 決めたこと | 理由 |
|---|---|
| **コードは20文字・100ビット**。文字は `23456789ABCDEFGHJKMNPQRSTUVWXYZ#`（0 / O / 1 / I / L を除くと31文字なので `#` を足した。利用者が選択） | 読み違えやすい文字を使わず、100ビットを保つ |
| **DB には鍵なしの SHA-256 のハッシュだけを保存する**（決定事項 3 の HMAC から変更） | 100ビットの乱数は鍵が無くても総当たりで戻せない。鍵を使うと交換のたびに全員のコードが使えなくなる |
| **コードの消費は、新しいパスキーの登録と同じトランザクションで行う**（入力の時点では照合だけ） | 入力の時点で消費すると、生体認証の取り消しだけで二度と戻れなくなる |
| 差し替えは `where: { id, recoveryCodeHash: 照合したハッシュ }` の条件つき更新で、資格情報の作成より**先に**行う | 同じコードの同時リカバリーは先の1つだけが通る。順序を逆にすると PostgreSQL でデッドロックになった |
| **リカバリー中は専用のトークン**（typ `kakebo-recovery+jwt`、10分）で、パスキーの登録しかできない | コードを入れただけの状態で家計データに触れさせない |
| 照合の失敗は「間違い・使用済み・制限」を区別しない一律の文言。`LoginAttempt` で IP 単位に制限する | 何が起きたかを外に教えない |
| **古いパスキーは自動で消さない** | コードを盗まれてリカバリーされたとき、本人まで締め出されないように |
| コードは設定画面から作り直せる（デモユーザーは不可）。作り直しの前の再認証はまだ求めない | 表示を見逃した人の逃げ道。再認証はセッションの個別失効と一緒に考える |

## 作業開始時の注意（2026-09-16）

- **コードは個人用kakeboからコピーして改修する。** テスト1612件とパスキー実装を活かすため
- **git履歴は持ち込まない。** `.git` をコピーせず、新規に `git init` する。個人用の履歴とdocsには、実データが入った本番環境のURL、実際の口座構成、予算額が含まれている
